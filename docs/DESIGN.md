# NekoTab 设计文档

本文面向维护者，记录实现取舍与关键细节；功能概览见 [README](../README.md)，
使用细节见 [FEATURES](FEATURES.md)。

## 关键设计

**Feature 隔离。** 依赖按编译目标切开，`sqlx` / `tokio` / `dotenvy` / `reqwest` /
`tower-http` 只在 `server` 下启用，`js-sys` / `gloo-timers` / `web-sys` /
`wasm-bindgen` 只在 `web` 下启用：

```toml
[features]
default = []
web    = ["dioxus/web", "dep:gloo-timers", "dep:js-sys", "dep:wasm-bindgen", "dep:web-sys"]
server = ["dioxus/server", "dep:sqlx", "dep:tokio", "dep:dotenvy", "dep:anyhow", "dep:reqwest", "dep:tower-http"]
```

WASM 产物里不含数据库驱动与 HTTP 客户端；服务端二进制里不含浏览器 JS 绑定。

**连接池初始化。** 建池是异步的，而 `OnceLock::get_or_init` 只接受同步闭包，
所以在 `main` 里先 `await db::init_pool(...)`，再 `set` 进 `OnceLock`。建池时
开 `create_if_missing`、`journal_mode = WAL`，并执行 `sqlx::migrate!` 跑迁移；
同时会补建数据库文件与图标目录的父目录。

**分类只由分组承担。** 早期版本的分类标签页由书签的 `tags` 去重派生，代价是无法
给分类排序、配图标，且一条书签带多个标签就会在多个标签页里重复出现。于是改成显式的
`groups` 表：一条书签归属至多一个分组（`NULL` 即「未分组」，不占一行、由前端合成）。

**标签从此退出界面。** 中途一度把标签作为"第二个筛选维度"加回首页（分组下面一行
标签 chip），并给了表单一个标签选择器；实机一看就是"两排分组"，用户直接问
"为啥需要加个标签分类"。回头看，这正是当初重构掉的东西——**分类入口只能有一个**，
多一个就会让人问"这俩有什么区别、我该用哪个"。所以标签的界面全部撤掉：首页那一行、
表单里的标签字段、批量打标签、`tag_bookmarks` 接口都不再存在。

数据库那一列**保留不动**（列是迁移加的，删列要新迁移，而迁移一旦部署就不能改；
更要紧的是不能悄悄丢数据）。导入仍然把文件夹路径写进它，搜索也仍然匹配它——
`工作/项目A` 里的 `项目A` 因此还是搜得到，只是没有地方显示"标签"这个概念了。

分组的删除是「归位」而非级联：`delete_group` 在同一个事务里把组内书签的
`group_id` 清空，书签本身不动。读列表时前端还会把「指向已不存在的分组」当作
未分组处理，兜住并发删除这类边角——否则那条书签在任何分类下都看不见。

**列表恒为全量，筛选与分页都在客户端。** 书签列表始终取全部
（`list_bookmarks("")`），分类筛选、关键词筛选、分页都只影响**显示**。
这样拖拽重排永远作用在完整顺序上。服务端那套按关键词的 AND/OR 模糊搜索仍然
保留（`POST /api/list_bookmarks` 传 `{"query":"..."}` 即可用），客户端为
「输入即筛」把它搬到了本地，两边口径一致。

**拖拽排序：把视图内的新顺序合并回全量顺序。** 分页和筛选让「看见的」变成全量的
一个子集，直接按视图下标写 `sort_order` 就会把别的书签挤乱。所以落位时用
`move_to_position(全量, 被拖的 id, 落点 id)`：它先算出目标在**全量**里的下标，
把被拖项从原位置摘掉再插进去，写回服务端的始终是**完整顺序**。这个函数还会校验
两个 id 确实在全量列表里，不满足就返回 `None` 整个放弃——排序是低频操作，
多一次比较换来「任何输入都不会把顺序弄乱」。同一个函数顺带把跨页拖拽变成免费的：
落点在第二页的卡片上时，目标下标本来就是全量的下标，不需要为跨页写任何特例。

**跨页拖拽靠分页按钮当落点。** 拖动过程中指针经过上一页 / 下一页按钮时自动翻页，
所以那两个按钮带 `data-page-flip="prev"|"next"` 标记，指针移动时先做一次属性命中
测试（`data_attr_at`），命中就翻页并带 700ms 节流，避免一掠而过翻好几页；
没命中再去找卡片。翻页后用 `elementFromPoint` 也能命中新页的卡片，
于是落位自然正确。

**拖拽走 Pointer Events，鼠标与触屏同一条路径。** 原生 HTML5 拖放在触屏上不触发，
而且 `<a>` 的默认拖拽会把链接地址当拖拽数据，两者会打架。所以按下时尽力把指针
捕获到卡片上（拖出网格也能继续跟踪），**判定与落点计算则放在网格这一层**——
网格是所有卡片的公共祖先，指针捕获失败时移动事件仍会从下方的元素冒泡上来，
拖拽不会因此失效。落点用 `document.elementFromPoint` 做命中测试，
比逐个读卡片矩形便宜。位移超过 8px 才算拖动，抬手后那一次 `click` 会被吞掉，
不会顺手弹出修改弹窗。

**长按与拖拽共用按下事件。** 普通态按下 500ms 且期间位移不超过 8px 才进入编辑态；
编辑态按下则直接进入待拖拽状态。触屏上编辑态的卡片带 `touch-action: none`，
否则拖拽会被浏览器当成滚动手势。

**删除是软删除。** `deleted_at` 置时间戳，列表查询一直带
`deleted_at IS NULL`，所以回收站里见到的是「删了但还在库里」的那些；
只有「彻底删除」才真的 `DELETE`。误删的代价从「不可恢复」变成「点两下还原」。

**站点图标落盘，库里只留元数据。** 图标字节写在 `ICON_DIR`
（默认 `data/icon`）下的独立文件里，`favicons` 表只存
`content_type` / `file_name` / `fetched_at`。这是有意的：几十 KB 一张的图标
塞进 SQLite 会让 `mtab.db` 迅速膨胀，备份、WAL 和 `VACUUM` 都跟着变重，
而图标本来就是可重取的缓存。写盘用「先写 `.tmp` 再改名」，避免半个文件被当成
图标读走并缓存。

**文件名不含域名。** `ls data/icon` 不该把收藏了哪些站点暴露出来，所以落盘名是
「时间戳 + 序号 + 主机名」混出的哈希加扩展名（如 `928615185a1c….ico`）；
同一主机的文件名记在 `favicons.file_name` 里，重复请求命中缓存不会再生成。

取图顺序：`/favicon.ico` → 首页声明的 `<link rel="icon">` → `/apple-touch-icon.png`。
每一步都必须校验 `Content-Type` 是 `image/`——实测 `claude.ai` 对任意路径都返回
`200 + text/html`，不校验就会把整个网页当成图标存下来。声明里**内联的 `data:`
URI 也支持**（现代站点与 SPA 模板常这么写，早先直接跳过等于白丢一类图标），
base64 与百分号编码两种都认。

**取不到图标必须回退成首字色块，而这里有个 hydration 时序坑。** 卡片是"彩色首字
打底、站点图标用 `<img>` 盖在上面，图标的白色底盘正好挡住首字"（底盘是必要的：
很多图标是透明底的浅色设计，直接压彩色渐变会看不见）。取不到时靠 `onerror` 把
`<img>` 撤掉、露出首字——**但这件事光靠 `onerror` 会漏**：`error` 事件不冒泡，
而图标请求是 SSR 那段 HTML 里就开始的，同源 `/icon/{host}` 返回 404 往往比 wasm
下载还快；等 hydration 把 `onerror` 挂上去，事件早发完了。于是那些卡片会一直顶着
浏览器的"碎图"占位符（它还把首字盖住了），看起来就像"图标全挂了"。
所以 hydration 之后由网格补查一次 `naturalWidth`（`dom::mark_broken_favicons`），
给已经失败的 `<img>` 打上 `data-broken`、交给 CSS 隐藏。两条路各管一段：
补查负责"挂监听之前就失败的"，`onerror` 负责"之后才失败的"（以及后来才新增的卡片，
它们的监听是创建时就挂好的）。

这个接口**只服务本站已收藏的站点**：要探测就得先加书签，顺带把这个按 host
代取的接口被当成任意出站探测（SSRF）入口的风险压掉了。设置 `ACCESS_PASSWORD`
后它与其他数据入口一样需要登录。取不到时写一条空数据的负缓存，
**有效期 6 小时**——早先设的是 7 天，但一次瞬时失败（容器刚起、DNS 还没就绪、
对方站点抖一下）就会把图标钉死很久，界面上看起来就是"图标全挂了"。取不到时
还会往服务端日志打一行**逐步原因**（如
`取不到图标 x.com：favicon.ico: 不是图片（text/html）；首页未声明任何图标；apple-touch-icon.png: HTTP 404`），
设置里也有「清空图标缓存」可以立刻全部重新代取。

**新增书签自动抓标题：复用取图标的 head 抓取，只填空位。** 服务端代取（浏览器直连
会被跨域挡），抓取那一层直接用 `favicon::server::fetch_html_head`——同一份 UA、8 秒
超时、"只读到 `</head>` 或 256 KB"、以及"不是 HTML 就不是页面"的校验，不必为标题
再写一遍。`page_meta.rs` 只做解析：`og:title` / `twitter:title` 优先于 `<title>`
（后者常带「页面名 - 站点名」后缀），描述取 `meta[name=description]` /
`og:description`；实体解码、空白折叠（源码里的缩进会原样进标题），再按**字符**截断
（名称 120、描述 300）。没有引入 HTML 解析 crate：要认的语法只有"标签名 + 带引号的
属性"这一小块，几十行扫描器足够，还能脱离网络单测。

回填写在表单这一层：**只填空着的字段**，用户已经打好的名称 / 描述不会被顶掉；只有
手动点「重新抓取」才覆盖名称（那是明确的"以页面为准"的意图）。抓取失败只显示一句
提示，不挡住保存——名称仍有服务端校验兜底。新增时若在网址框里直接回车提交，保存
流程会先抓一次再写库，所以"粘贴网址 → 保存"也能拿到标题。

不做额外的出站白名单：它和「添加书签」是同一层权限（设了 `ACCESS_PASSWORD` 就一起
要登录），而给内网 / 本机服务收藏书签是正常用法，挡掉私有地址反而误伤。编码按 UTF-8
解，仍在用 GBK 的老站点标题可能乱码——不值得为一个辅助功能引入编码表，用户改一下
名字即可。

**删除的撤销走"提示条 + 软删除"，不再另造一套撤销栈。** 删除本来就是软删除
（`deleted_at` 置时间戳），所以"撤销"只要把那几条的 `deleted_at` 清回去即可——
位置、分组、图标、排序都还在原处，不存在"恢复得对不对"的问题。于是提示条里存的是
**被删掉的 id**，点「撤销」就调 `restore_bookmarks`，和回收站里那条路是同一个接口。

为什么不干脆只留回收站：回收站那条路要"开设置 → 翻分区 → 找那条 → 点还原"，
误删的人多半懒得走完这条四步的路径，于是那条书签就永远躺在回收站里。提示条把这条路
缩短到一次点击，六秒后自己消失（自动消失用的是一个递增令牌：期间又删了别的，
令牌变了，这次的定时器就不去动那一条）。

**访问统计单独一张表，而不是给书签加两列。** 访问记录是**会一直长大的流水**，
混进 `bookmarks` 意味着每次列表查询都要多带两列与排序无关的数据，而书签本身
（去重、导出、图标缓存）完全不需要知道自己被打开过几次；"最近 30 天"这类时间窗
在流水表上是一条 SQL，在计数列上则做不到——次数是累计的，砍不出窗口。
流水表会长，但增长很慢（一次点击一行），写入路径每 50 次修剪一次、只留最近 5000 条。

**「最常访问」组件的取数放在服务端聚合。** 客户端拿到的不是原始流水，而是一份
join 好、排序好、截好顶的清单（id / 标题 / 网址 / 次数 / 最后访问时间）。
组件与书签共用一张表（见下节），组件本身没有网址，所以这条统计只认书签。

**死链检测分三种结果，"连不上"不等于"坏链"。** 这是这一节最要紧的判断：
服务器能探到的地址，和用户浏览器能打开的地址根本不是一回事——内网地址
（`192.168.x.x`）、需要登录的站点、被墙的域名、或者服务器所在网络到不了的域名，
全都探不出来。把它们算成"坏链"再给一个"批量删除"按钮，是会误删东西的。
所以状态分成三类：`ok` / `broken`（有响应但状态码是错的）/ `unreachable`
（连不上）；**只有 broken 标到卡片上、也只有 broken 提供一键清理**。
3xx（换地址）与 401 / 403（要登录）都算"活的"。

探测用 HEAD 省流量，但有些服务器不认 HEAD（405 / 501），这时退回 GET 再试一次——
把"方法不被允许"误判成"链接坏了"是最容易犯的错。并发封顶 8 条、每条超时 6 秒
（比他处代取的 8 秒短：一次要探几十条，每条都慢 8 秒的话整轮要等好几分钟）。
结果写回书签行（`link_status` + 检查时间），卡片上才能直接显示"这条可能坏了"。

**搜索提交必须走 JS，不能用原生表单。** 最初的做法是
`<form method="GET" action="{引擎地址，%s 已替换}">`，指望浏览器直接导航过去。
**这是错的**：按 HTML 规范，表单 GET 提交会**替换** action URL 里原有的查询串，
于是搜索词被清空，实测拿到的是 `https://www.baidu.com/s?`（查询词没了）。
而且各引擎参数名不同（百度 `wd`、谷歌 `q`、必应 `q`），还有把词放在路径里的
模板，原生表单无法通用地表达。所以改为拦掉原生提交、由 JS 精确打开那个 URL。
`window.open` 由用户手势（点击 / 回车）触发，不会被弹窗拦截；表单上仍保留
`action` / `target` 作为「JS 没跑起来」时的静态兜底。

**引擎存在数据库里。** `engines` 表带 `active` 标记与 `prefix` 前缀。
前缀在服务端会被规范化为「小写 + 只留字母数字与连字符」，并拒绝与其他引擎重复；
前端只在「前缀独立成段且后面还有关键词」时才认它，避免把 `github` 拆成 `gh` + `ithub`。

**一言由服务端代取。** 浏览器不直接访问 `v1.hitokoto.cn`，而是调用自己的
`get_quote` server function，由服务端发请求。这样避开跨域、统一做 8 秒超时；
失败时前端保留上一条。`reqwest::Client` 用 `OnceLock` 复用，避免每次请求重做
TLS 握手。

**搜索联想只认已知引擎。** 输入时列出当前引擎给的联想词，点一下或回车即用它去搜。

有两个绕不开的约束，都落在设计里：

* **必须服务端代取。** 浏览器的 suggest 接口普遍不带 CORS 头，前端直连拿不到响应。
* **端点只按引擎 id 反查，绝不接受客户端传地址。** 各家联想接口的格式互不相同
  （百度 `{"g":[{"q":…}]}`、必应 `["词",[…]]`、360 `{"result":[{"word":…}]}`、搜狗是
  一段 JSONP），没法像搜索地址那样用一个 `%s` 模板通吃，所以是一张写死的表。如果
  让客户端传 URL 进来，这个后端代取接口立刻变成任意出站请求的入口（SSRF），和
  `/icon/{host}` 只服务已收藏站点是同一个取舍。

**联想的防抖与"过期响应丢弃"。** 每敲一个字就发一次请求太吵，所以停 180ms 才发；
但更麻烦的是**响应回来的顺序不保证**——按"a"和"ab"各发一次，可能"a"的结果后到、
把"ab"的结果盖掉。所以每次输入给一个递增令牌，回来的响应若发现令牌已经变了就丢掉。
引擎请求单独设 2.5 秒超时（比通用那 8 秒短）：联想要跟着手速走，慢就该当作"这家
没有联想"，而不是让面板悬在那里。失败一律返回空表、不报错——联想只是锦上添花，
出口抖一下、对方限流一次，都不该在界面上留下痕迹。

**时钟与农历的 SSR 一致性。** SSR 阶段无从得知「现在」，因此时钟首屏渲染空串，
挂载后由 `use_future` 每秒刷新。服务端与客户端首次渲染结果一致，不会 hydration
失配。农历、第几天、第几周都是纯计算，跟着每秒刷新一起算，不发任何请求。

**主题与背景分成两层。** 主题只换 CSS 变量（`[data-theme="light"]` 里重定义
一批变量），组件规则一行都不用改。背景分两个绝对定位层：底衬层（默认渐变或
内置预设，由 CSS 类决定）与壁纸层（内联 `background-image`）。这么分是因为
dioxus 的解释器在把 `style` 设成空串时，会把「之前设过、现在没了」的内联属性
**补回来**——于是「清空背景图」要刷新才生效；壁纸层改成始终显式写
`background-image: none` 或 `url(...)`，属性一直有值，就没有可补的东西。
两层分开则让「内联图片」和「CSS 渐变」不会互相覆盖。

**背景轮换在客户端算，且哪儿都不存东西。** 池里的选择发生在首页：拿"每次打开"的
时间戳（本来就为绕图片缓存生成的那个 nonce）散列出下标。随机源只在客户端存在，
所以轮换开启时背景要等 hydration 之后才出现——与 v1.6 随机图那套是同一个取舍。
**选中的那条既不回写设置、也不写 `localStorage`**：前者会让每个新标签页都写一次库、
多标签还会互相覆盖，后者是新标签页不该往浏览器里留的东西。代价有两个，都写在设置
的说明文案里——设置里高亮的那张在轮换开启时只是"默认张"；池里只有两张时有 1/2 的
概率连着两次给同一张。另外随机参数只追加到外链地址上——本机的 `/wallpaper/xxx`
内容不会变、响应本来就带 `immutable` 长缓存，追加只是白下一次请求（这是对 v1.6
行为的一处小修正）。

**快捷键要挂在可聚焦的节点上，首屏还得主动送焦点进去。** 键盘事件靠焦点冒泡，
所以根节点带 `tabindex="0"`。但页面加载完成后 `document.activeElement` 是
`<body>`，而 body 不在根节点子树里——挂在根上的 `Esc` / `Ctrl+K` / 翻页键
一个都收不到。所以挂载后主动把焦点送进搜索框（只在焦点确实无处可去时）。
另外「方向键翻页」只在焦点位于**有内容的**输入框时才让路：搜索框默认聚焦，
若只按标签名判断，翻页键就永远用不上，而空输入框里本来也没有光标可移。

**设置是键值表，加字段不需要迁移。** `settings` 表是 `key`-`value`，读写由
`Settings::from_pairs` / `to_pairs` 一对方法收口（写在一起，避免读写漂移），
取值范围也在那里统一夹好。所以新增外观类、开关类的设置项只改 Rust 代码，
不碰数据库；只有加表或加列才需要新的迁移文件。目前 18 个设置项都存在这张表里
（书签自定义图标是**加列**，所以走了迁移 003）。

**导入解析在服务端。** 浏览器导出的 Netscape HTML 解析（文件夹栈 → 分组、
实体解码、`<DD>` 描述）放在 `transfer.rs` 里做，纯函数、有单测。

**浏览器 HTML 的文件夹路径：首层分类进分组。** 分组取
**第一个非容器文件夹**——浏览器导出时会把所有书签套在一个容器文件夹里
（`书签栏` / `Bookmarks bar` / `其他书签` 等），那不是用户的分类，跳过它才能让
标签栏显示真正的顶层分类；用整条路径当分组名会拼出一堆长名字，用最内层则会让
「工作/项目A」和「工作/项目B」变成两个看不出共同上层的平级分组。更深层级的路径
仍然完整写进 `tags` 列（界面上不显示，但搜索会命中），所以信息没有丢。JSON 备份按
里面的分组名还原（导出写分组名，导入按名字对应，不存在就建）。

**容器文件夹既不当分组，也不进 `tags`。** 浏览器会把所有书签套在一个容器里
（书签栏 / Bookmarks bar / 其他书签…），那不是用户的分类。一开始只在分组那侧跳过了
它，`tags` 那侧仍旧照收，于是人人都多出一个「书签栏」——它不表达内容，拿它检索等于
命中全集，纯属噪音。现在两侧共用同一个 `is_container_folder` 判断。

文件读取走 `<input type="file">`，但**不把 FileReader 的回调直接接回 Rust**：
那段 JS 交给 `document::eval` 跑，读到的文本通过 `dioxus.send` 发回来，之后所有
动作都在 `onchange` 事件触发的那次 `spawn` 里做。这里踩过一个坑——原生 JS 回调
不在任何 Dioxus 作用域里，在其中写 signal 或调用 `spawn`，会让 dioxus-core 取
「当前作用域」时 `unwrap` 到 `None` 直接 panic；release 下 `panic = "abort"`，
于是整个页面死掉，现象只有控制台一句 `RuntimeError: unreachable`。
这条约束对任何 wasm 应用都成立：**原生 JS 回调里只该碰不依赖运行时状态的东西**。

**装了 panic 钩子。** 同样是 `panic = "abort"` 的后果：wasm 里 panic 只会变成一个
没有信息的 `unreachable`。钩子在 abort 之前把消息与位置打成一行 `console.error`，
并写进一个固定 id 的 DOM 节点（`#nekotab-panic`）——应用崩死之后那个节点还在，
从外部也能读到现场。上面那个坑就是靠它定位到 `runtime.rs:223` 的。

**分组图标塞进原来的 `icon` 字段，不新增表结构。** 图标值有四种形态：
`i:code`（内置图标）、`t:#rrggbb:字`（文字图标）、`http…`（图片地址）、空串（名称首字）。
内置图标是自己画的简单几何图形（`src/components/icons.rs`，24×24、线框、23 个），
不引第三方图标库：避免为几十个图标引入依赖与许可问题，而且这些形状够简单、肉眼可核对。
三个用到图标的地方（标签栏、分组管理、批量移动）走同一个渲染函数，免得样式漂移。
书签的图标（迁移 003 加的 `bookmarks.icon` 列）复用同一套取值约定，所以内置图标集、
校验函数、渲染函数都直接用现成的。

**上传壁纸走原始字节，不用 multipart。** 只需要传文件，而 multipart 要额外引
解析依赖，所以 `POST /wallpaper` 的请求体**就是图片字节**，类型由 `Content-Type`
给出，浏览器侧一个 `fetch('/wallpaper', { method: 'POST', body: file })` 就够。
文件名由服务端生成（不透明哈希 + 由 MIME 推的扩展名，原始文件名一律丢弃，
免得把用户的路径信息带进容器），删除与回发都靠**白名单式**的
`is_safe_name`（只接受「十六进制 + 已知扩展名」，挡住 `../` 与任意后缀）。
壁纸与图标是两种东西：图标是可再生缓存，有负缓存、有「清空图标缓存」；
壁纸是用户自己的数据，只由用户显式增删，不参与任何自动清理。

**请求体上限得自己放开——axum 默认只收 2 MB。** 壁纸单张上限是 16 MB，而 axum 对
`Bytes` 这类提取器的默认上限是 2 MB：超了会在**读请求体**时就被 413 掉，而且连接是
中途掐断的，浏览器只报一句 `TypeError: Failed to fetch`——我们写的那句"图片过大
（上限 16 MB）"根本没机会显示（实测：3 MB 的图直接撞这个坑，而 1 MB 以下一直没暴露
出来，因为此前测的都是小图）。两处修：`main.rs` 在 router 末尾挂一层
`DefaultBodyLimit::max(MAX_WALLPAPER_BYTES)`（`Router::layer` 作用于此前注册的全部
路由，dioxus 的 server function `/api/*` 也在内——书签导入传的是整份备份文本，
同样吃这个上限，一份 3 MB 的导出以前会以同样方式失败）；前端在选择文件时先看
`file.size`，超限的直接不发请求，当场说清是哪张、多大。

**背景池只存地址，本机文件靠地址回到目录。** 池（`settings.background_urls`，
一行一个地址）是"有哪些背景"的唯一出处，本机图在池里就是 `/wallpaper/xxx.png`
这个地址——于是轮换、缩略图、删除都只需要处理字符串，不必为"外链还是本地"
分两套数据。为什么不直接把目录列举当池：**首页渲染时只有 `Settings` 可用**（它
随首屏直出，见下文），去列目录要多一次请求、还赶不上首屏；而池随设置一起到达。
`background_url` 保留成"当前生效的那条"（池非空时必定是池里的一条），渲染路径
因此一行没改。老库里只有这一个字段，读的时候把那条当成池里的唯一一条——纯函数、
幂等、不写库，于是这个改动不需要迁移。

**「存到本地」是 server function，不是新路由。** 上传必须走原始字节路由（形状
不同），但"给我一个地址、我去取回来"的输入输出都是 JSON，正是 server function
的形状。抓取复用站点图标那套代取（`backend::http_client()`、带 UA、确认是图片
才收），两点不同：体积上限按壁纸算（16 MB）且**边读边卡**——图标是"全读进内存
再看大小"，壁纸按那个写法会被一个几百 MB 的响应打爆；失败原因（超时 / 不是图片
/ 超限 / HTTP 状态）要直接摆到界面上。

**背景池面板的 HTTP 也放在 JS 里。** 和读文件同理（见上文 Dioxus 作用域那条），
上传要拿 `<input type="file">` 的 `File` 对象、删除要拼 URL，干脆在
`document::eval` 里发请求，只把结果 `dioxus.send` 回 Rust。这样客户端不必再引
一个 fetch 库。

**设置面板是"左菜单 + 右内容"两栏。** 加进分组管理与回收站之后，单个 400px
抽屉从上滚到底太长了；现在左边选分区（外观 / 背景 / 卡片与布局 / 时钟与一言 /
打开与翻页 / 数据 / 分组管理 / 回收站），右边只看这一节，两栏各自滚动。
设置类分区共用一套"草稿 + 保存设置"，其余分区各自有即时生效的操作，所以保存条只在
设置类分区出现。

**背景那一节是例外：它改完即时落库。** 上传一张图、点一下"设为当前"、拖一下遮罩，
都是"看着调"的动作——改完还要再点一次「保存设置」才生效，用起来就是"我传了图什么
都没发生"（真发生过）。所以这一节用一个 effect 盯着草稿里背景那五项（渐变、池、
当前、遮罩、轮换开关），与"已落库的那版"不一致就去存：睡 400ms 再存（拖滑块会连发
input 事件），存完再看一眼，直到两者一致。其余设置项仍是手动保存——它们是偏好，
改完不急着落库。

**导出走普通 axum 路由而不是 server function。** `/export/bookmarks.json`、
`/export/bookmarks.html`、`/export/db.sqlite` 都注册在 `dioxus::server::router` 上，
浏览器直接以文件形式下载（带 `Content-Disposition: attachment`），客户端不需要
任何 Blob/下载相关的 wasm 胶水，也能用 curl 直接验证。数据库快照用
`VACUUM INTO` 而不是拷文件：`mtab.db` 在 WAL 模式下还有 `-wal` / `-shm` 兄弟文件，
直接拷走主文件会丢掉未 checkpoint 的写入，`VACUUM INTO` 出来的才是自洽单文件。

Netscape HTML 的导出于导入是对称的：分组写成文件夹（`<H3>` + 嵌套 `<DL>`），
未分组的放根层，属性值做实体编码。写这个导出时被自己的往返测试抓到一个老 bug：
**解析端没做实体解码**，浏览器导出时会写 `&amp;`，于是带 `&` 的 URL 会原样存进库。
现在 href 与 ICON 都会先解码再入库。

**响应压缩。** 静态产物（wasm / js / css）由 dx 在构建期压成 `.br`
（`Dioxus.toml` 的 `pre_compress`，质量 11），`dioxus-server` 的
`ServeFile::precompressed_br()` 直接把那份发出去、运行时零 CPU；`main.rs` 里
再挂一层 gzip + brotli 负责动态响应（SSR 的 HTML、server function 的 JSON）。
实测 wasm 1058 KB → gzip 423 KB → brotli 326 KB。

## 迁移与回退

数据库迁移随二进制编译进去（`sqlx::migrate!`），启动时自动应用，没有单独的迁移步骤。

**正向可以，反向不成立。** 拿旧镜像跑已经升级过的库会直接启动失败，报
`migration N was previously applied but is missing in the resolved migrations`
——sqlx 默认不允许"库里已应用、而当前二进制里没有"的迁移。回退镜像时得先把多出来的
那几条记录从 `_sqlx_migrations` 里删掉（列本身可以留着，旧代码不认识就不会碰）。

**007 是个例外。** 它给 `bookmarks` 加了 `group_ids` 列；只删迁移记录、留着列的话，
之后再升级回带 007 的版本会因 `ALTER TABLE ... ADD COLUMN group_ids` 报
`duplicate column name` 而启动失败。要回退到 007 之前再升回来，先执行
`ALTER TABLE bookmarks DROP COLUMN group_ids;`（SQLite ≥ 3.35）或直接用升级前的备份。
旧镜像运行时只会写 `group_id`；新版本读取时会把主分组补进 `group_ids` 的归属里，
所以降级期间改过的分组不会在新版本里凭空消失（但可能同时出现在旧分组和目标分组下，
彻底对齐需要重新编辑一次该卡片）。

**迁移是「基线 + 追加」**：`001_init.sql` 是合并后的单一基线，它**一旦被部署过就不能再改**
——sqlx 会校验已应用迁移的校验和，改动会导致启动直接失败
（`migration N was previously applied but has been modified`）。这条踩过两次。
今后任何表结构变更都必须**新增**文件。迁移 002 把 `favicons` 表整个重建（字节改落盘），
旧的图标缓存会丢失并在下次访问时重取——它是纯缓存，这是有意的取舍。迁移 005 给
`bookmarks` 加了 `kind` / `config` 两列来承载组件，默认值都是空串，所以对既有数据是
零行为变化。

## 组件复用书签表

**组件与书签共用一张表、一套顺序**（`bookmarks.kind`：空串是书签，`clock` 是数字时钟）。
好处是拖拽、跨度、编辑态、`data-bookmark-id` 落点这些都不用为组件重写一遍；代价是
凡"只该管书签"的地方都要按 `kind` 收口，现在有四处：列表查询带上两样再由前端分流、
导出排除组件、URL 去重与查重加上 `kind = ''`、`clean_bookmark` 按 kind 走两条校验。
加新组件只动 `models::WIDGET_KINDS` 与渲染分支。

**组件的参数存在 `config` 这个 JSON 串里**，服务端按 kind 规范化后才落库（多余字段
丢掉、缺的按默认补上），客户端解析失败一律回落默认值。所以脏数据只会让某张卡片
显示成默认样式，不会让整页渲染不出来。
